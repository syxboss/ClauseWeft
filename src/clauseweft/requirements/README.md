# requirements · 需求版本与验收条款

对应 **F04 / A05、A07**。本模块持久化需求的版本和基线；每条评审意见的处理轨迹归 reviews。

## 数据所有权

每个需求保留原始意图、上下文引用、候选原稿、条款 ID、验收条件、未决问题与版本摘要。并行起草可产生同源的多个版本，负责人选择或整合后记录来源及采纳理由。已发布的版本不可原地覆盖；需求基线指向已获负责人接受的特定版本。

| Python 操作 | 输入与结果 | 主要失败 |
|---|---|---|
| 创建或修订需求版本 | 原始输入或父版本、预期版本、条款及修改理由 → 不可变新版本、变更条款 ID | 预期版本过时、条款 ID 重复、没有验收条件 |
| 比较和整合草案 | 同源版本集合、逐项选择及理由 → 条款级差异或新候选稿 | 相互矛盾的选择未裁决 |
| 接受需求基线 | 候选版本摘要、该稿评审状态、负责人决定 → 基线引用，产生下游可消费事件 | 阻断意见未关闭、意见指向旧稿、修改部分尚未重评 |

调用者在同一个工作区写事务内执行 `revise(conn, run_id, parent, clauses, reason, actor, required_reviewers)` 和 `freeze(conn, run_id, version, actor, reason)`。条款采用 `{"id":"CSV-01","text":"项目管理员可导出","acceptance":"普通用户收到拒绝"}`。新版本记录变更的条款 ID，撤销旧基线、候选与交付的当前指针。`list_specs` 可以查看历史稿与当时的批准决定，`compare` 按条款 ID 比较两个版本。

**验收例**：v2 只写“管理员可导出”。负责人将权限来源细化为服务端项目角色后产生 v3。旧版本意见和审批保留在历史里，只有 v3 的受影响条款经复核并获负责人接受，workflow 才可让编码分支读取这一基线。
