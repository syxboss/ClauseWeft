# workflow · 阶段依赖与并行汇合

对应 **F03 / A03、A04**。图的来源由运行方式决定。

| 入口 | 何时确定依赖 |
|---|---|
| `single` | 创建一个模型节点 `task`。用户选定角色时，节点读取服务端保管的角色和技能快照 |
| `complex` | 先创建 `plan`。该节点交回有效分工后创建 `branch-1` 等并行分支，并令 `summary` 依赖所有分支 |
| `tool` | 指定一个工具时使用拟参、审批和答复三个节点。指定 `allowed_tools` 时从 `decide-1` 开始，每项提议产生一个待审批节点。只有批准并写入回执才生成下一轮，模型提交有效答复后结束 |
| `workflow` | 启动时编译内置 `delivery-v1`，或校验已发布的交付模板保留所有必需关卡 |
| 已发布的通用 SOP | 按发布快照中的模型、人工关卡和依赖创建图 |

在复杂任务中，模型只返回 `{"subtasks":["分工说明","另一项说明"]}`。服务端接受 2 至 8 项非空文本，每项最多 4,000 个字符，负责分配节点 ID、阶段和依赖。规划回执与扩图在同一事务处理，过期或重复回执无法增加节点。所有分支使用已有租约调度，可由同一模型承担。需要互相独立的评审时，使用下述独立模型分组。

## 已发布 SOP

模板由 Agent 节点和人工审批节点构成，节点声明阶段、上游依赖、提示与可选的固定模型。发布时校验悬空引用、循环、节点类型及独立模型分组，运行前按拓扑顺序保存私有副本。角色提示、模板版本和模型绑定冻结在该次运行中，后续编辑模板不会改变在途运行。

通用 SOP 复用正常调度器的授权复核、预算预留、网关派发、回执和历史产物。审批节点等待操作者处理后才解锁下游，退回指定上游会使依赖它的节点进入新世代。暂停保留已经发出的调用及费用，停止新派发与下游推进，恢复后继续。仅包含审批节点的 SOP 可以在未配置模型时运行。

完整研发模板继续保留需求基线、补丁整合、实测和交付接纳的必需依赖，角色设置在既有输出格式约束内生效。通用 SOP 产物不会自动取得代码交付批准。仓库实测继续使用已登记的隔离执行器。

## 调度模型

workflow 拥有流程图、阶段及任务节点、必需/可选分支、输入产物引用和依赖边。单任务也是只包含所需节点的图。完整流程先产出需求基线，再解锁编码与测试设计；候选提交形成后，代码评审可与测试执行并行。运行生命周期和实际调用归 runs。

`max_concurrency` 限制同时活跃节点数。`pinned_endpoints` 可按节点指定端点。完整流程的两路需求评审以及实现与测试设计各自使用独立模型身份。独立评审者读取同一冻结稿，提交反馈前互不读取对方结论。组内某个必需分支失败，保留其余成功结果；当前模板所有节点都为必需节点。

| 工作流操作 | 输入与结果 | 主要失败 |
|---|---|---|
| 编译运行计划 | 入口、阶段配置、角色和依赖、仓库基准 → 图与输入版本清单 | 循环依赖、悬空边、缺少必需角色 |
| 查询可执行节点 | 运行 ID、图版本、上游状态/审批、当前并发 → 可派发节点和阻塞原因 | 未接受需求、未解决冲突或独立模型数不足 |
| 汇合/计算失效范围 | 分支完成事件或上游输入变化 → 更新节点、可复用与需重跑的分支 | 输入摘要已过期、取消后收到晚到产物 |

`compile(plan)` 固化角色、提示、依赖与独立模型分组；`allocate(choices, occupied)` 为整组选取不同身份，并保留已成功或仍在执行的成员。节点就绪和失效处理由 runs 在同一业务事务内推进。

**验收例**：两个模型分别执行必须等待另一路开始才会返回的评审任务。应观察到两条实际尝试的时间重叠、输入版本相同；其中一路失败时汇合仍阻塞。需求未被接受时，编码分支的实际调用数为零。
