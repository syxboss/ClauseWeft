# storage · SQLite 与本地工件存储

为 **F01–F08** 提供持久化，关键验收为 **A07、A08、A09**。`Store(state_dir)` 在指定目录维护 `workspace.sqlite3` 及 `objects/`，使用 Python 3.11+ 标准库。

## 写入与恢复

SQLite 采用 WAL 模式，以事务写入业务记录、幂等标识、状态变更及待处理工作；工作线程领取持久任务表中的任务并使用有期限的租约。需要原子预算裁决时使用短写事务，模型调用、Git 和测试进程都在事务外。工件按内容摘要落在受控目录；先完整写入并验证内容，再发布数据库引用。恢复要求可以从有效业务记录定位与其摘要匹配的工件。

| 持久化操作 | 输入与结果 | 主要失败 |
|---|---|---|
| 开启事务并提交业务写入 | 事务范围内的存储操作、幂等键和预期版本 → 同时提交或回滚 | 写锁遇竞争时有限等待；唯一约束或过期版本冲突不允许双写 |
| 领取和确认持久任务 | 领取者、租约、任务状态/版本 → 经原子领取的任务或空结果 | 租约过期可再检查；已可能向外发送的尝试先对账，不能靠重领直接重发 |
| 保存/读取工件 | 工件内容或摘要 → 摘要、大小及受控引用，或经校验的内容 | 摘要不匹配、引用缺失或写入失败，阻止发布对应业务结果 |

`transaction()` 在同一线程复用连接并以保存点支持嵌套调用。`stage_blob(data)` 持久化内容并返回 SHA-256，业务事务记录归属；`read_blob(sha)` 读回时重新验证摘要。`events_after(run_id, after, limit)` 按序号读取已提交事件。runs 发起业务领取和状态更新，storage 提供条件更新所需的持久化操作。

**验收例**：两个工作线程争抢最后一笔预算，重启后查询仍只有一笔有效预留；重复收到同一结果不新增有效交付物。历史报告保持可读，当前放行通过版本关联另行判断。
