## 功能结构

LoopForge 把团队项目中的需求、Agent 角色、标准 SOP、运行记录和人工审批连在一起。Chat 支持探索与迭代，SOP 承担可重复的执行步骤，两条入口关联相同需求。角色配置与节点执行分开，运行页面提供节点产物和日志，等待人的决定集中到审批入口。这些做法可以帮助重复性团队协作，但不能直接推导为 ClauseWeft 的默认操作路径。[产品主线与功能清单](https://github.com/Tencent/LoopForge#features)

| 观察到的 LoopForge 组织方式 | ClauseWeft 的采用边界 | 可选能力 |
|---|---|---|
| 项目承载需求及交付工作 | 项目整理任务与授权，独立需求在需要跟踪时使用 | 项目管理、可选需求与运行关联 |
| Agent 角色被多个 SOP 复用 | 角色职责、提示与模型绑定独立维护 | 角色表单、SOP 角色引用与执行快照 |
| SOP 有节点、依赖、审批和发布版本 | 团队可以保存并复用工作方式 | 模型和人工关卡的图编辑、发布和执行 |
| 审批集中在统一收件箱 | 仅在显式选择含审批的执行方式时显示待办 | 需求基线、通用关卡、交付审批 |
| 每次执行有状态、工具及产物记录 | 任务详情需要以阶段与证据为中心 | 节点状态、事件、答复、补丁、实测与账目 |
| 团队账号与项目设置 | 企业使用需要稳定身份、操作权和审计 | 密码账号、会话、实例角色与业务审计 |

LoopForge 官方还描述了编码 CLI、脚本、子 SOP、沙箱、托管仓库交付和扩展工具。ClauseWeft 本次围绕已有 HTTP 模型网关和隔离交付执行器建立平台层，后续按明确适配器与验收计划接入这些执行方式。[SOP 节点说明](https://github.com/Tencent/LoopForge#how-sops-work) · [部署及执行环境](https://github.com/Tencent/LoopForge/blob/main/docs/deployment.md)

## 架构启发

LoopForge 的公开架构把图调度和租约放在 engine，把持久化放在 repo，把 API、执行环境、执行机器及代码托管适配分开。其公开版使用账号密码和 GitHub 适配接入既有用户、令牌、仓库及交付契约。ClauseWeft 延续模块化边界，在已有调度、网关、工作区和测试模块之上补充平台业务层，避免把页面数据保存在浏览器临时状态中。[架构原文](https://github.com/Tencent/LoopForge/blob/main/docs/architecture.md)

## 产品决策

ClauseWeft 聚焦多模型协作研发执行。用户从目标和内容开始，默认创建项目、提交任务、读取结果与证据。模型由管理员自行接入，动态路由、多模型独立评审、受限补丁、真实测试和费用核对继续作为执行能力。角色、技能、需求、SOP 与审批按具体任务启用，当前导航将相应资源放入“协作”分组。

企业要求主要体现为可靠执行、清晰权限、可解释成本和完整审计。普通任务采用少量步骤，代码交付保持必要的审批和实测门槛。本轮默认路径与高级协作分别验收。SSO、组织目录、每项目独立角色与自定义授权、互不信任租户隔离、分布式执行、托管代码自动提交、其他 CLI 与 MCP 接入继续按目标环境扩展。[产品需求](01-产品需求.md) · [验收基线](02-需求评审.md)
